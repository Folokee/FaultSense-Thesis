\section{Introduction}
This chapter details the implementation of the anomaly detection and fault diagnosis methods explored during this project. It covers the model architectures, training procedure and results
obtained from the evaluation on the Costa dataset.

\section{Tools and Experimental Setup}
\subsection{Software and Libraries}
The modeling pipeline is implemented in Python. Its main libraries are the following.

\begin{itemize}
    \item \textbf{PyTorch} and \textbf{PyTorch Lightning:} the deep learning framework and the training-loop layer used to define the neural architectures and to organize their training, validation, and checkpointing; \textbf{torchmetrics} computes training-time metrics.
    \item \textbf{Scikit-learn:} preprocessing, classical ML baselines, and evaluation metrics.
    \item \textbf{Optuna:} hyperparameter parameters optimization.
    \item \textbf{pandas}, \textbf{Polars}, \textbf{NumPy}, and \textbf{PyArrow:} tabular data structures, high-performance transformations, array computation, and Parquet storage across the pipeline stages.
    \item \textbf{SciPy:} scientific computing utilities for numerical routines and statistical operations.
    \item \textbf{Matplotlib} and \textbf{seaborn:} diagnostic plots and result figures such as precision-recall curves and confusion matrices.
    \item \textbf{loguru:} structured logging across the pipeline stages.
\end{itemize}

\subsection{MLOps Infrastructure}\label{sec:implementation-experimental-setup}
The experimental work reported in this chapter spans a large configuration matrix: several candidate models per task and multiple feature profiles. Producing results that are reproducible and comparable across this matrix requires the operational discipline that Machine Learning Operations (MLOps) brings to production machine learning systems. The experimental infrastructure is accordingly organized as an MLOps stack resting on three versioned and traceable layers: the code and its component architecture, the configuration that specifies each individual experiment, and the data and pipeline lineage that links every reported metric to the exact inputs that produced it. Figure~\ref{fig:mlops-topology} shows how the supporting toolchain realizes these three layers.

\paragraph{Codebase structure.}
\begin{itemize}
    \item \texttt{data/} - pipeline stages (ingestion, split, preprocess, featurize), each exposed as a module entry point.
    \item \texttt{modeling/} - task-specific trainers with shared infrastructure (HPO, artifact contracts, cross-validation). A \texttt{run.py} dispatcher per task reads \texttt{active\_model} from config and routes to the corresponding trainer; switching models requires only a config change.
    \item \texttt{evaluation/} - leakage checks and result figures.
    \item Every run produces a standardized artifact bundle (serialized model, feature manifest, calibration parameters, configuration snapshot) validated at load time before any inference.
\end{itemize}

\paragraph{Configuration as the experiment specification.}
Every experiment is fully defined by two YAML files:
\begin{itemize}
    \item \textbf{data\_config.yaml} - active dataset, split policy, preprocessing flags, and feature profiles. Profiles form an additive ablation ladder: each level extends the previous through boolean flags.
    \item \textbf{model\_config.yaml} - shared experiment parameters (seeds, CV folds), per-task HPO settings (sampler, pruner strategy, trial budget, per-model search spaces), and model-specific calibrations.
\end{itemize}

\paragraph{Data and pipeline lineage.}
\begin{itemize}
    \item \textbf{DVC} tracks all large artifacts (raw data, processed tables, model checkpoints) by content hash; only the lightweight \texttt{.dvc} pointers are stored in Git. Any upstream change automatically invalidates and regenerates the affected downstream artifacts.
    \item \textbf{MLflow} logs each run's dataset identifier, feature profile, HPO parameters, and validation and test metrics, so that every reported figure is traceable to the exact data state and configuration that produced it.
    \item \textbf{DagsHub} hosts the DVC remote and the MLflow tracking server on a single platform, linking versioned data, code commits, and experiment runs.
  \end{itemize}

\paragraph{Compute environments.}
\begin{itemize}
    \item \textbf{Classical ML models} that do not require GPU are trained locally on an AMD Ryzen 7 PRO 6850U (8 cores, up to 4.7~GHz).
    \item \textbf{Deep learning models} are trained on Google Colab Pro+, which provided access to an NVIDIA A100 GPU (6912 CUDA cores, 80~GB HBM2e, 312~TFLOPS FP16) for all deep learning training and HPO runs.

\paragraph{Hyperparameter optimization protocol.}
% Model selection is conducted with Optuna using the Tree-structured Parzen Estimator (TPE) sampler. Classical models are tuned with fixed trial budgets, where each trial is fast and therefore pruning is not required. Deep learning models use the same Optuna interface but can additionally enable early stopping and pruning strategies, because training a single trial can span multiple epochs. For all tasks, the validation partition is the only split used for HPO decisions (metric optimization and threshold selection), while the test partition is reserved for final reporting.
Each model exposes a set of hyperparameters (learning rate, regularization coefficients, architectural dimensions) that govern its capacity and training dynamics but cannot be determined by the training procedure itself. Selecting them requires a separate optimization process driven by a held-out validation signal. Given the size of the search space and the non-trivial cost of individual trials for deep learning models, a systematic automated search is necessary.

Two complementary optimization strategies are employed depending on the model family. For most classical and deep learning models, optimization is performed using Optuna \citep{akiba2019optuna} with the Tree-structured Parzen Estimator (TPE) sampler \citep{bergstra2012random}. TPE builds a probabilistic model of the objective from the history of completed trials and focuses subsequent sampling on regions associated with good outcomes. This sequential, model-guided search concentrates the evaluation budget on the most promising configurations as trials accumulate - an approach that works well when individual trials are expensive and the overhead of maintaining a surrogate model is justified by the trial cost.

The second strategy is the Good-point-set Vectorised Snow Ablation Optimiser (GVSAO), a population-based metaheuristic derived from the snow ablation algorithm \citep{GTBADGVSAOTransformerBiLSTMbasedTimeseries2026}. GVSAO initialises a population of candidate solutions using a 
good-point-set method that ensures uniform coverage of the search space from the first generation. Each candidate is evaluated on the objective, and the population is refined over successive generations through dual-population dynamics that balance exploration and exploitation: one sub-population performs local refinement around high-quality solutions while the other maintains diversity by searching less-visited regions. Adaptive melting factors 
modulate the intensity of this competition across generations, and periodic oscillation mutations inject 
controlled randomness to prevent premature convergence. Unlike TPE, which builds a probabilistic model of the objective surface from trial history, GVSAO directly navigates the parameter space through coordinated agent movement, making it suitable when the evaluation budget is small and the overhead of maintaining a surrogate model would outweigh its benefit. Figure~\ref{impl:fig:gvsao} illustrates the GVSAO workflow.

    \centering
    \includegraphics[width=0.8\textwidth]{figures/detection/gvsao.jpg}
    \caption{Good-point-set Vectorised Snow Ablation Optimiser (GVSAO) workflow.}
    \label{impl:fig:gvsao}
\end{figure}

Each HPO study runs on the fixed original train/val split and completes before the K-fold cross-validation begins, so the winning configuration is fixed for all folds. The test partition is invisible throughout. The optimization objective is the validation macro PR-AUC for anomaly detection and the validation macro F1 for fault classification, consistent with the headline metrics of Section~\ref{sec:evaluation-methodology}. Among configurations whose scores fall within one standard deviation of each other, the simpler configuration is preferred as a tiebreaker.

The pruning strategy is adapted to trial cost. For classical ML models, no pruner is applied: trials are inexpensive and no intermediate epoch-level signal is available. For deep learning models, a Median pruner is added: a trial is terminated when its intermediate validation score falls below the median of all completed trials at the same epoch, after a warmup period during which pruning is suspended. Within-trial early stopping patience scales with the trial epoch budget, preventing premature termination on short trial budgets.

\section{Conclusion}
This chapter implemented and evaluated a two-stage Fault Detection and Diagnosis (FDD) pipeline on the Costa PV dataset. Its two winning models point to the same conclusion about where modelling complexity is warranted. For anomaly detection, \textbf{PC-Flow (baseline\_raw)} is the strongest model, achieving a macro PR-AUC of $0.990 \pm 0.005$ under 5-fold episode-stratified cross-validation; the ablation study shows that physics conditioning drives this gain, while the flow's learned representation makes additional hand-engineered features redundant. For fault diagnosis this relationship is reversed: \textbf{ExtraTrees} wins with a macro F1 of $0.959 \pm 0.078$ and the lowest cross-fold variance of the three tree ensembles evaluated, and its feature importances confirm that the engineered physics features (not the raw signals) carry the discriminative information. A lightweight classical ensemble already attains this accuracy, so the added cost of a deep classifier is not justified for this task. Physics knowledge is therefore the unifying element across both stages (supplied to the flow as a conditioning signal and to the trees as explicit features) and it is this domain grounding, rather than raw model capacity, that makes the pipeline both accurate and efficient: a deep model where the representation must be learned, a shallow one where the right features are already known.
