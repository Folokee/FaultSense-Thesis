\section{ONNX Export and Artifact Contract}
\label{sec:deployment-onnx}
% ────────────────────────────────────────────────────────────

The trained PC-Flow model is exported to the Open Neural Network Exchange (ONNX) format using \texttt{torch.onnx.export}. The export procedure is designed to produce a batch-generalizable ONNX graph rather than a batch-1-baked artifact: coupling layer masking uses \texttt{index\_select} (which maps to ONNX \texttt{Gather}) and concatenation rather than boolean-mask indexing, which would bake the batch dimension as a constant. The ONNX graph is verified using \texttt{onnxruntime} on a held-out calibration set to confirm numerical agreement with the PyTorch reference to a tolerance of $10^{-5}$ on the log-likelihood output.

Each deployed artifact is accompanied by a \textbf{deployment contract}: a structured metadata file that records:
\begin{itemize}
    \item the expected input tensor shape (batch, feature dimension);
    \item the ordered list of feature names, in the order expected by the model;
    \item the StandardScaler parameters (mean and scale) estimated from the training partition;
    \item the physics conditioning channels $c = (\text{irr}, \text{pvt})$ and their indices in the feature vector;
    \item the calibrated tier parameters consumed by the alarm engine (Section~\ref{sec:deployment-alerting}): the sensitive (P3) threshold, the conformal (P2) threshold, the CUSUM (P1) reference slack $k$ and control limit $h$, and the normal-score statistics $(\mu_{\mathrm{normal}}, \sigma_{\mathrm{normal}})$ used for the CUSUM $z$-transform;
    \item the timestamp of the training run and the validation score at checkpoint.
\end{itemize}
The contract is verified at load time before inference begins: the runtime checks that the feature list in the incoming data stream matches the contract's ordered feature list, applies the stored scaler, and validates the threshold provenance. Any contract violation raises a runtime exception before the first inference is executed.

\section{Development}

\subsection{Architecture Overview}

The FaultSense monitoring system follows a two-tier local client--server architecture: a Python backend owns the inference pipeline, drift monitoring, and data management, while a web-based JavaScript frontend owns the operator interface. The two tiers communicate exclusively through persistent WebSocket connections — an outbound channel on which the backend pushes inference results, drift status, and hardware metrics to the dashboard at the sensor sampling rate without polling, and an inbound channel on which the backend receives operator commands (stream control, retraining requests, artifact approval). A separate WebSocket channel ingests sensor rows from an external bridge process, decoupling acquisition from inference.

\subsection{Backend}

The backend is written in Python 3 and is structured around three concurrent threads that share a thread-safe output queue:

\begin{itemize}
    \item The \textbf{inference loop} dequeues sensor rows, applies the feature engineering and scaling pipeline, scores each row through the PC-Flow ONNX model via the alarm engine, conditionally invokes the CatBoost classifier, updates the Page-Hinkley drift monitor, and pushes the result onto the output queue.
    \item The \textbf{readings loop} forwards the raw sensor measurements to the frontend for visualization, independently of the inference cadence.
    \item The \textbf{metrics loop} reads CPU, GPU, memory, and temperature from the hardware layer and pushes rolling inference statistics to the dashboard once per second.
\end{itemize}

The ingest server runs on a separate asyncio event loop in a daemon thread, receiving sensor rows over a second WebSocket channel and placing them on a thread-safe queue that the inference loop drains. Table~\ref{tab:backend-stack} summarizes the principal backend dependencies.

\subsection{Frontend}

The frontend is a self-contained single-page application written in vanilla JavaScript with no build step. It communicates with the backend exclusively through the WebSocket connection established at startup and auto-reconnects on disconnect. The key frontend components are:

\begin{itemize}
    \item \textbf{Real-time charts}: animated score and sensor readings charts rendered on HTML5 Canvas elements using Chart.js, with a configurable rolling time window.
    \item \textbf{Event log}: a chronological log of all alarm events with filter controls, implemented in \texttt{event-log.js}.
    \item \textbf{Drift panel}: a reactive drift stage indicator that updates on each \texttt{drift\_status} push from the backend and exposes the retraining request controls when the stage reaches action-ready.
    \item \textbf{PDF export}: client-side report generation using jsPDF, producing a maintenance report from the in-memory event log without any server-side file I/O.
\end{itemize}

\subsection{Deployment Mode}

On the Jetson Nano the application is launched via \texttt{python main.py}. The launcher auto-selects the GUI backend: PyQt5 with QWebEngineView is preferred when available, falling back to pywebview, then to a plain browser mode that serves the frontend over a local HTTP server and opens it in the default browser. In all modes the backend and frontend communicate over \texttt{localhost}, and no network interface is exposed outside the device.

\section{Tiered Alerting System}
\label{sec:deployment-alerting}
% ────────────────────────────────────────────────────────────

The alarm engine implements a three-tier priority hierarchy aligned with the ISA-18.2 alarm management standard \citep{isa182011alarm}. Each tier corresponds to a distinct threshold policy applied to the same PC-Flow NLL score, so the choice of tier does not affect the underlying model — only the decision boundary at which an alarm is raised. The three tiers and their calibration policies are as follows.

\begin{description}
    \item[P3 Advisory] The sensitive threshold calibrated at a false-positive rate of 20\% on training-normal scores. This tier maximizes recall and is intended as an early-warning indicator: the operator should \emph{investigate} when a P3 alarm fires, but no immediate intervention is required. A P3 Advisory alarm is shown in amber on the dashboard.

    \item[P2 High] The conformal threshold derived from the distribution-free conformal prediction framework, providing a false-positive rate guarantee of $\alpha = 0.05$ under the exchangeability assumption. This tier offers a statistically principled high-precision boundary: \emph{schedule inspection} when a P2 High alarm fires. A P2 High alarm is shown in orange.

    \item[P1 Critical] The CUSUM-based alarm: a one-sided cumulative sum chart accumulates signed deviations of the NLL score from its reference level and fires when the accumulated statistic exceeds the calibrated control limit. Because CUSUM integrates evidence across consecutive samples rather than evaluating each sample independently, it is insensitive to single-sample spikes and fires only on sustained score shifts. This tier achieves sample-level precision of 100\% in evaluation and requires \emph{immediate action}. A P1 Critical alarm is shown in red.
\end{description}

The P3 threshold thus governs early sensitivity, P2 provides a high-confidence actionable boundary, and P1 is reserved for events that have persisted long enough for the CUSUM accumulator to confirm a genuine sustained deviation.

\section{Drift Detection}
\label{sec:deployment-drift}
% ────────────────────────────────────────────────────────────

A deployed anomaly detector is only reliable as long as the operational data distribution remains close to the training distribution. PV system behaviour evolves over time: module ageing, seasonal soiling, inverter firmware changes, and weather regime shifts can all move the distribution of normal-class NLL scores, causing the calibrated threshold to become either too permissive or too restrictive without any indication to the operator.

The drift detection module monitors the physics channel $\tilde{P}_{\mathrm{corr}}$ (temperature-corrected, irradiance-normalised power) using a bidirectional \textbf{Page-Hinkley (PH) test} \citep{page1954continuous}. The physics channel is used as the primary trigger rather than the model score itself to avoid the circularity that arises when a stale model's own score is used to judge whether the model is stale. The score channel is monitored in parallel as an advisory-only readout. The PH statistic accumulates signed deviations from a running reference:

\[
    M_t = \sum_{i=1}^{t}\bigl(x_i - \bar{x} - \delta\bigr), \quad
    \mathrm{PH}_t = M_t - \min_{1 \leq j \leq t} M_j, \quad
    \text{drift} = \mathbf{1}[\mathrm{PH}_t > \lambda],
\]

where $\bar{x}$ is the running mean, $\delta$ is a sensitivity margin against ordinary fluctuations, and $\lambda$ is the control limit. The monitor escalates through two stages — \emph{advisory} after $N_{\mathrm{adv}}$ consecutive PH detections, and \emph{action-ready} after $N_{\mathrm{act}} > N_{\mathrm{adv}}$ — with a 1-hour cooldown that suppresses repeated events after an operator action. Figure~\ref{fig:deployment-drift-tikz} illustrates the PH accumulator behaviour over a simulated deployment window.

\section{Conclusion}
\label{sec:deployment-conclusion}
% ────────────────────────────────────────────────────────────

This chapter has presented the complete deployment of the FaultSense monitoring system on the NVIDIA Jetson Nano. The artifact contract (Section~\ref{sec:deployment-onnx}) enforces consistency between the training environment and the operational inference environment at load time. The ISA-18.2 three-tier alarm system (P3~Advisory, P2~High, P1~Critical) maps three calibrated threshold policies — sensitive, conformal, and CUSUM — to actionable priority levels that allow plant operators to triage alerts without reading alert text. The software stack (Python backend, vanilla-JS frontend, WebSocket communication) was chosen to minimise dependencies on the constrained aarch64 platform while delivering a responsive single-page operator interface. The Page-Hinkley drift detector monitors the physics channel independently of the model score to avoid circularity, and escalates through advisory and action-ready stages before enabling the operator-gated model update workflow.
