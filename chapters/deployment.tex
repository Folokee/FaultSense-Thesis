\subsection{Drift Detection}
\label{sec:deployment-drift}
% ────────────────────────────────────────────────────────────

A deployed anomaly detector is valid only while operating conditions remain within the range seen during training. In PV fault detection that range is narrow: the majority of labelled datasets come from short induced-fault campaigns that cover at most one season, so the model never observes the full annual variation in irradiance and module temperature it will later face. When deployed conditions drift outside that window, the calibrated thresholds lose their guarantees without signalling any error to the operator. The drift module is an additional layer in the system that surfaces this situation before it silently erodes detection quality.

The module therefore monitors the \emph{operating regime} $(\mathrm{irr}, T_{PV})$ — the conditioning inputs the detector relies on — to detect when deployed conditions move outside the training envelope. A bidirectional \textbf{Page-Hinkley (PH) test} \citep{page1954continuous} is applied to daily-aggregated regime statistics, so that persistent seasonal shift is distinguished from the expected diurnal cycle:

\[
    M_t = \sum_{i=1}^{t}\bigl(x_i - \bar{x} - \delta\bigr), \quad
    \mathrm{PH}_t = M_t - \min_{1 \leq j \leq t} M_j, \quad
    \text{drift} = \mathbf{1}[\mathrm{PH}_t > \lambda],
\]

where $\bar{x}$ is the running mean, $\delta$ is a sensitivity margin, and $\lambda$ is the control limit. The monitor escalates through two stages: an \emph{advisory} after $N_{\mathrm{adv}} = 7$ consecutive shifted days and \emph{action-ready} after $N_{\mathrm{act}} = 14$ days.

\subsection{Architecture Overview}

The monitoring system follows a two-tier local client-server architecture: a Python backend owns the inference pipeline, drift monitoring, and data management, while a web-based JavaScript frontend owns the operator interface. The two tiers communicate exclusively through persistent WebSocket connections: an outbound channel on which the backend pushes inference results, drift status, and hardware metrics to the dashboard at the sensor sampling rate without polling, and an inbound channel on which the backend receives operator commands (stream control, retraining requests, artifact approval). A separate WebSocket channel ingests sensor rows from an external bridge process, decoupling acquisition from inference. \subsection{ONNX Export and Artifact Contract}
\label{sec:deployment-onnx}
Both deployed models are exported to ONNX for runtime inference on the Jetson Nano. The PC-Flow anomaly detector is exported from PyTorch using \texttt{torch.onnx.export}. The graph is kept batch-generalisable by avoiding boolean-mask indexing during export and using ONNX-compatible gather and concatenation operations instead. The exported model is validated with ONNX Runtime on a held-out calibration set, with log-likelihood outputs matching the PyTorch reference within $10^{-5}$.

The Extra Trees fault classifier is converted from scikit-learn using \texttt{skl2onnx}. The ensemble is represented as an ONNX \texttt{TreeEnsembleClassifier}, preserving the original decision boundaries. The converted model is checked against the scikit-learn reference on the test set to confirm identical class predictions.

Each ONNX model is deployed with a metadata contract that defines the expected input shape, feature order, scaler parameters, physics-conditioning channels, alarm thresholds, CUSUM parameters, and normal-score statistics used by the alarm engine. The Extra Trees classifier is also deployed with a sigmoid probability-calibration file, which stores the class-wise calibration coefficients used to convert raw classifier scores into calibrated probabilities.

At startup, the runtime validates the incoming feature schema against the contract, applies the stored scaler, and checks the calibration and threshold metadata before inference begins. Any mismatch raises an error before the first prediction is executed.

\section{Real-Time Inference Performance}
\label{sec:deployment-latency}
% ────────────────────────────────────────────────────────────

A central premise of this work is that PV fault detection and diagnosis can be performed \emph{on the edge} (locally, on hardware inexpensive enough to be installed per site) rather than streaming raw measurements to a cloud service for every inference. Edge execution removes the round-trip latency, the dependence on continuous connectivity, and the recurring transmission cost that a cloud-inference architecture would impose on a permanently running monitor. This section validates that premise empirically: it shows that the full two-model pipeline meets the real-time constraint on the target device with a wide margin, and that the margin is a structural property of the design rather than an artifact of one configuration.

\paragraph{Measurement protocol.} The complete pipeline (feature engineering, PC-Flow anomaly scoring, the tiered alarm engine, and conditional fault classification) was exercised on the Jetson Nano by replaying 162\,453 real PV samples in acquisition order at the operational cadence of 1~Hz. Wall-clock time was recorded around each per-sample inference call, and the first 50 samples were discarded as warm-up. Latency is reported per stage and end-to-end as the median (p50), 95th, and 99th percentiles over the full replay (Table~\ref{tab:deployment-latency}). At 1~Hz the per-sample budget is 1\,000~ms.

\begin{table}[H]
\centering
\caption{Inference latency on the Jetson Nano (162\,453 samples at 1~Hz; budget 1\,000~ms).}
\label{tab:deployment-latency}
\begin{tabular}{lccc}
\toprule
\textbf{Stage} & \textbf{p50 (ms)} & \textbf{p95 (ms)} & \textbf{p99 (ms)} \\
\midrule
PC-Flow anomaly detector  & 8.97  & 13.58 & 19.04 \\
Extra Trees classifier    & 5.10  & 9.50  & 14.75 \\
\midrule

The full pipeline completes in 12.94~ms at the median and 30.04~ms at the 99th percentile, a margin of $77\times$ and $33\times$ respectively against the 1\,000~ms budget. Because the classifier is invoked only when the detector raises an alarm, the steady-state cost during healthy operation (the overwhelming majority of samples at a sound installation) is the detector path alone, at 8.97~ms median.

\paragraph{Inference cost breakdown.} When the PC-Flow model is timed in isolation (excluding feature engineering, alarm-engine routing, and dashboard broadcast) it completes in \textbf{565~µs} at the median and \textbf{970~µs} at the 99th percentile, accounting for less than 5\% of the total end-to-end latency. The dominant cost is therefore the surrounding pipeline, not the model itself.

This observation is consequential for the design rationale. PC-Flow was selected over larger deep baselines not only because it matched their detection quality (Section~\ref{sec:ad-tournament}), but because a compact detector is a prerequisite for a complete monitoring system to run within a single 1~Hz inference cycle on one device: the fault classifier, the alarm engine, and the drift monitor all execute in the same loop alongside the detector. A substantially larger model would remain within the 1\,000~ms per-sample budget in isolation, but would consume the latency margin required by the co-running components.


In summary, the pipeline meets the real-time requirement with a $33\times$ margin at the 99th percentile, and does so in a regime where orchestration, not inference, is the dominant cost. The system satisfies the edge-deployment objective in full, and retains clear headroom for higher sampling rates, additional monitored channels, or richer feature pipelines without approaching the real-time limit.

\section{Conclusion}
\label{sec:deployment-conclusion}
% ────────────────────────────────────────────────────────────

This chapter has presented the complete deployment of the FaultSense monitoring system on the NVIDIA Jetson Nano. The artifact contract (Section~\ref{sec:deployment-onnx}) enforces consistency between the training environment and the operational inference environment at load time for both the PC-Flow anomaly detector and the Extra Trees fault classifier, both exported to ONNX. The ISA-18.2 three-tier alarm system (P3~Advisory, P2~High, P1~Critical) maps three calibrated threshold policies (sensitive, conformal, and CUSUM) to actionable priority levels that allow plant operators to triage alerts without reading alert text. The software stack (Python backend, vanilla-JS frontend, WebSocket communication) was chosen to minimise dependencies on the constrained aarch64 platform while delivering a responsive single-page operator interface. The Page-Hinkley drift detector monitors the operating regime (the conditioning inputs) independently of the model score to avoid circularity, and escalates through advisory and action-ready stages before enabling the operator-gated model update workflow.
